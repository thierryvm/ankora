## 6. Le plan J1, et les deux défauts qu'il a fallu deux tours pour voir

Committé : [`docs/plans/J1-attribution-paiements.md`](../plans/J1-attribution-paiements.md),
sur `feat/j1-attribution-paiements` (`47a9514`). **Zéro ligne de code écrite.**

Deux verdicts `🟡 APPROVED WITH CHANGES`, quinze corrections. Les deux qui comptent :

1. **Ma migration monolithique aurait cassé la production.** Les migrations partent à la
   main, le code par merge — jamais simultanés. Colonne `NOT NULL` + ancien code déployé
   = `23502` sur chaque insert : **cocher une facture échoue** pour les 5 comptes réels.
   Aucun ordre ne marche. Motif expand/contract adopté.
2. **Ma correction ne corrigeait rien.** `supabase db push` n'applique pas « la prochaine »
   migration : il applique **tout ce qui manque**. Tant que le fichier B est dans l'arbre,
   il part avec A. Donc **B n'est pas écrit dans cette PR** — il naît dans une PR de suivi,
   après confirmation du déploiement. Un fichier absent ne peut être poussé par erreur ;
   c'est la seule forme qui ne repose pas sur la mémoire de l'opérateur, et l'opérateur est
   seul.

Autres corrections notables : **7 sites d'écriture** et non 2 — dont
`charge-conversion.ts:177-194`, qui copie dix champs d'une charge vers un engagement et
aurait perdu le onzième en silence. Et les preuves 1/2/3 sont des garanties **de base**
qu'aucun Vitest ne peut rendre (les tests d'action utilisent un faux client) : elles
deviennent une spec e2e authentifiée, donc **le plancher authentifié monte de 41 à 41 + N**
